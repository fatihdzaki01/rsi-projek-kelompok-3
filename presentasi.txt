  ## 🟦 ORANG 1: Arsitektur Sistem, Kontrak Protocol Buffers, & Envoy Proxy           
                                                                                      
  ### 1. Bagian Penjelasan (Apa yang diucapkan)                                       
                                                                                      
  │ "Selamat pagi/siang Pak Fajar. Pada proyek rewrite ini, kami memodernisasi        
  endpoint                                                                            
  │ monitoring campaign Berbagive dari REST menjadi gRPC. Tantangan utamanya adalah:  
  │ browser (Vue) tidak bisa langsung memanggil gRPC murni karena batasan HTTP/2      
  │ framing pada browser. Oleh karena itu, arsitektur kami menggunakan Envoy Proxy di 
  │ port 8090 sebagai penerjemah grpc-web menuju gRPC Server Python di port 50051."   
  │ "Semua kontrak data didefinisikan secara strictly-typed di dalam file Protocol    
  │ Buffers (monitoring.proto), mencakup request, detail campaign, dan daftar donatur 
  │ terbaru."                                                                         
                                                                                      
  ### 2. Cara Membuktikan (Aksi konkret di layar)                                     
                                                                                      
  1. Buka Terminal: Jalankan docker compose ps                                        
      • Tunjukkan ke dosen: "Ini container kami, Pak. Ada PostgreSQL (5434), Envoy    
      (8090), gRPC Server (50051), dan Nginx (8080)."                                 
  2. Buka File Proto di VS Code: Buka grpc-service/proto/monitoring.proto             
      • Tunjukkan pesan CampaignMonitoringUpdate dan service CampaignMonitoringService.
      • Tunjukkan 2 method: GetCampaignMonitoring (Unary) dan StreamCampaignMonitoring
      (Server-streaming).                                                             
  3. Buka File Envoy Config: Buka envoy/envoy.yaml                                    
      • Tunjukkan baris filter envoy.filters.http.grpc_web dan upstream cluster ke    
      port 50051.                                                                     
                                                                                      
                                                                                      
  ### 3. Konsep yang Harus Dipahami (Jika Dosen Bertanya)                             
                                                                                      
  • Kenapa butuh Envoy Proxy? Browser web tidak mengizinkan akses low-level ke HTTP/2 
  frames dan trailing headers yang dibutuhkan oleh native gRPC. Envoy bertindak       
  sebagai translator antara format gRPC-Web (HTTP/1.1 atau HTTP/2 kompatibel browser) 
  ke gRPC murni.                                                                      
  • Kenapa pakai Protocol Buffers (.proto)? Protobuf bertindak sebagai single source  
  of truth (kontrak baku). Kode client (JavaScript) dan kode server (Python) di-      
  generate dari file proto yang sama, mencegah human-error ketidakcocokan tipe        
  data/key JSON.

  ## 🟧 ORANG 2: Implementasi Server gRPC Python & Streaming Database                 
                                                                                      
  ### 1. Bagian Penjelasan (Apa yang diucapkan)                                       
                                                                                      
  │ "Saya bertanggung jawab atas backend gRPC service (server.py). Kami memilih Python
  │ (grpcio) karena Laravel/PHP-FPM bersifat stateless per request sehingga tidak     
  │ natural untuk streaming persisten. Server gRPC Python ini berjalan sebagai daemon 
  │ long-running pada port 50051, membaca database PostgreSQL yang sama secara        
  │ langsung, dan mengeksekusi logika streaming secara efisien."                      
                                                                                      
  ### 2. Cara Membuktikan (Aksi konkret di layar)                                     
                                                                                      
  1. Buka File Server: Buka grpc-service/server.py                                    
      • Tunjukkan fungsi query_monitoring_data() yang melakukan query SQL ke tabel    
      campaign, komunitas, dan donasi.                                                
      • Tunjukkan implementasi StreamCampaignMonitoring():                            
        while context.is_active():                                                    
            data = query_monitoring_data(campaign_id)                                 
            yield build_grpc_message(data)                                            
            time.sleep(3)                                                             
                                                                                      
  2. Tunjukkan Log Container: Jalankan di terminal:                                   
    docker compose logs --tail=20 -f grpc-service                                     
                                                                                      
      • Perlihatkan log: 🚀 gRPC Server running on port :50051 dan log request yang   
      masuk secara realtime.                                                          
                                                                                      
                                                                                      
  ### 3. Konsep yang Harus Dipahami (Jika Dosen Bertanya)                             
                                                                                      
  • Apa bedanya Unary RPC vs Server-Streaming RPC?                                    
      • Unary: 1 Request ➔ 1 Response (mirip REST GET biasa).                         
      • Server Streaming: 1 Request ➔ Banyak Response (yield) secara berkesinambungan 
      tanpa perlu request baru dari client.                                           
  • Bagaimana server tahu jika user menutup browser? Menggunakan context.is_active()  
  dan menangani exception GeneratorExit. Ketika client disconnect, server otomatis    
  menghentikan loop agar tidak terjadi resource/memory leak.

      = 1;

      sama sekali!"                                                                   
                                                                                      
                                                                                      
  ### 3. Konsep yang Harus Dipahami (Jika Dosen Bertanya)                             
                                                                                      
  • Bagaimana lifecycle stream diatur di Vue? Stream diinisiasi lewat client.         
  streamCampaignMonitoring() dan di-listen lewat event .on('data'). Ketika komponen   
  dihancurkan (misal pindah halaman), lifecycle hook onUnmounted() otomatis memanggil 
  grpcStream.cancel() agar koneksi tidak menggantung.                                 
  • Kenapa REST tadi tidak update otomatis? Karena REST berbasis Pull (client yang    
  harus berinisiatif meminta data baru). Sedangkan gRPC streaming berbasis Push       
  (server yang berinisiatif mendorong data baru ke browser).

  ## 🟥 ORANG 4: Benchmark, Analisis Perbandingan Data, & Kesimpulan
  
  ### 1. Bagian Penjelasan (Apa yang diucapkan)
  
  │ "Untuk membuktikan efisiensinya secara kuantitatif, kami membuat skrip pengujian  
  │ performa independen (benchmark_rest.py dan benchmark_grpc.py) yang menguji kedua  
  │ protokol dengan 100 request dan 10 warmup request pada beban data yang sama       
  │ persis."
  
  ### 2. Cara Membuktikan (Aksi konkret di layar)
  
  1. Buka Terminal & Tunjukkan Hasil JSON:
      • Buka file benchmark/rest_result.json dan benchmark/grpc_result.json.          
      • Atau jalankan scriptnya langsung:
        python3 benchmark/benchmark_rest.py
        python3 benchmark/benchmark_grpc.py
  
  2. Paparkan Hasil Perbandingan Data Nyata:
      • Ukuran Payload: REST menghasilkan 1.271 bytes, sedangkan gRPC hanya 481 bytes 
      (Hemat 62,2% bandwidth).
      • Kecepatan Latency: Rata-rata latency REST adalah 24,17 ms, sedangkan gRPC     
      adalah 16,46 ms (31,9% lebih cepat).
      • P95 Latency: REST di angka 28,43 ms, sedangkan gRPC di angka 20,33 ms (gRPC   
      lebih stabil pada ekor distribusi latency).
  3. Sampaikan Kesimpulan Akhir:
  │ "Kesimpulannya, gRPC terbukti jauh lebih unggul dalam throughput, ukuran transfer,
  │ dan latency untuk fitur real-time monitoring. Namun trade-off-nya adalah          
  │ kompleksitas infrastruktur tambahan (butuh Envoy proxy dan compiler protoc)       
  │ dibanding REST yang plug-and-play."
  

  ### 3. Konsep yang Harus Dipahami (Jika Dosen Bertanya)
  
  • Kenapa payload gRPC bisa 62% lebih kecil dari REST? REST memakai format teks JSON 
  di mana nama field (seperti "dana_terkumpul", "nama_lembaga") berulang dikirim      
  sebagai teks. Protobuf membuang nama string dan mengompresnya menjadi bilangan tag  
  biner (1 byte) dan encoding integer varint.
  • Kenapa gRPC bisa lebih cepat? gRPC berjalan di atas HTTP/2 dengan binary framing  
  dan koneksi TCP yang multiplexing (tidak perlu handshake TCP dan SSL berulang-ulang 
  seperti HTTP/1.1 pada REST).
